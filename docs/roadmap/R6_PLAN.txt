creates a new Android application identity.

will not automatically transfer its local SharedPreferences progress
to the new application.

before the first formal portfolio release.

Do NOT implement migration from the old development application ID.

10. R6.1 — ANDROID RESPONSIVE/LAYOUT MINIMUM
============================================================

Problem:

Pre-R6 audit found two concrete narrow-screen layout risks
on ordinary Stage 2 paths.

A. MultimeterBlock

Three ports approximately 88 px each are placed in one row.

At narrow Android widths, after parent/card/meter padding,
available width can be smaller than the required row.

B. VoltageDropBlock

Measurement point row has a fixed horizontal requirement
that can exceed available width around a 360 px viewport.

These are release blockers until corrected and tested.

READY requires:

- no P0;
- no unresolved supported-flow P1;
- narrow-screen blockers resolved;

- application identity finalized;
- branding no longer stock Flutter;
- provenance blocker resolved;
- README substantially current;

- analyze clean;
- tests green;
- diff check clean.

CI failure caused by configuration is NOT acceptable for READY
if CI was added as part of R6.

Screenshots should be present for full portfolio readiness.
If screenshots alone remain missing but everything else is release-safe,
report explicitly rather than hiding it.


============================================================
68. STOP CONDITIONS
============================================================

STOP and request owner decision if:

1. applicationId change requires unexpected migration work;

2. Android package rename causes broader platform changes
than expected;

3. approved launcher artwork is unavailable at R6.3;

4. battery replacement artwork is unavailable at R6.4;

5. another asset has unclear provenance with meaningful
public-release implications;

6. MIT licensing conflicts with an existing repository constraint;

7. responsive fix requires changing simulator semantics;

8. integration test requires large production architecture changes;

9. physical Android smoke finds a release-blocking defect;

10. release build fails after R6 changes;

11. CI requires changing supported SDK/dependencies substantially;

12. secrets or credentials are discovered;

13. signing work would require storing credentials in repository;

14. any R6 task begins requiring a new product feature.

============================================================

R6 succeeds when the project can credibly be shown to:

- an employer;
- a Flutter developer;
- a technical interviewer;
- a portfolio reviewer;
- a person installing the Android demonstration APK.

The repository should communicate:

what the application does,
why it exists,
how it is structured,
what is technically interesting,
how it is tested,
how to run it,
what it supports,
and what it deliberately does not support.

The application should feel like a deliberate v0.1.0,
not an unfinished Flutter template.

============================================================
73. AUTONOMOUS EXECUTION BOUNDARY
============================================================

The agent may proceed autonomously through tasks that have
all required approved inputs.

However:

R6.3 requires approved launcher artwork.

R6.4 requires replacement battery artwork.

R6.6 physical-device smoke requires actual human/device execution
unless the environment genuinely exposes an Android device.

Therefore autonomous execution must STOP when one of those inputs
is unavailable.

Do not substitute placeholder artwork merely to finish the plan.
