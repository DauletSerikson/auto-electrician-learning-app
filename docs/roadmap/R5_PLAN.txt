1. ГЛАВНАЯ ЦЕЛЬ R5
============================================================

Сделать существующую систему прогресса:

- тестируемой;
- надёжной при сохранении;
- устойчивой к ошибкам;
- предсказуемой при navigation;

============================================================
2. ФАКТИЧЕСКАЯ СЕМАНТИКА ПРОГРЕССА
============================================================

Persistent progress сейчас означает:

«множество ID уроков, которые пользователь успешно завершил
и явно подтвердил кнопкой завершения».

Не сохраняются:

- ответы;
- score;
- количество попыток;
- состояние симуляторов;
- положение щупов;
- диагностическая история;
- состояние текущего quiz attempt;
- время прохождения;
- дата прохождения.

Это намеренное разделение:

PERSISTENT PROGRESS
=
completed lesson IDs

SESSION / ATTEMPT STATE
=
answers, correctness, retry, simulator state, current score

Не смешивать эти две категории без отдельного product decision.


============================================================
3. CURRENT PROGRESS ARCHITECTURE
============================================================

Основные роли:

ProgressService
- читает completed lesson IDs;
- записывает completed lesson IDs;
- сейчас также выполняет часть общей агрегации.

LessonScreen
- хранит session attempt state;
- принимает callbacks от task widgets;
- вычисляет completion/scoring;
- запускает persistent completion.

ModuleScreen
- читает completed IDs;
- показывает completed state уроков.

HomeScreen
- получает общий progress snapshot;
- показывает общий процент;
- показывает следующий урок.

HomeProgress
- вычисленный read model;
- не является persisted entity.

LessonCompletion
- content policy завершения;
- не является фактом пользовательского completion.

LessonSummary
- content projection.

CourseLesson
- связывает module context и LessonSummary.

Не объединять эти модели только из-за похожих названий.


============================================================
4. SOURCE OF TRUTH
============================================================

Persistent lesson completion:

membership lesson ID в completed_lessons.

Module completion:
не реализован.

Module percentage:
не реализован.

Overall course progress:
актуальные CourseLesson + completed IDs.

Current lesson attempt:
локальное session state LessonScreen.

Current quiz score:
локальное session state текущей попытки.

Saved quiz completion:
тот же completed lesson ID.

Score отдельно не persist.


============================================================
5. CURRENT LESSON COMPLETION CONTRACT
============================================================

Для обычного lesson:

open lesson
→ новая session attempt
→ выполнить все оцениваемые задания
→ все задания должны быть correct
→ становится доступна кнопка завершения
→ пользователь нажимает кнопку
→ lesson ID сохраняется
→ экран возвращает successful result
→ родительский progress обновляется.

Если оцениваемых заданий нет:
кнопка завершения доступна сразу.

Если пользователь просто выполнил задания, но не нажал кнопку:
persistent completion не создаётся.

Если пользователь ушёл назад:
persistent completion не создаётся.

Reopen completed lesson:
создаётся новая session attempt.

Повторное успешное completion:
должно быть логически идемпотентным.


============================================================
6. CURRENT QUIZ CONTRACT
============================================================

Формула:

totalTasks = количество оцениваемых task blocks

correctAnswers = количество true results

scorePercent =
round(correctAnswers / totalTasks * 100)

passed =
all tasks answered
AND
scorePercent >= passingScore

Каждое задание имеет одинаковый вес.

Retry отдельного task разрешён.

Quiz является тренировочной проверкой:
пользователь может исправить ошибку после feedback.

Score не сохраняется.

Persistent completion создаётся только после успешной попытки
и явного нажатия кнопки завершения.


============================================================
7. ОБЯЗАТЕЛЬНЫЕ QUIZ CONTRACTS
============================================================

Stage 0:

5 tasks
passingScore = 80

3/5 = 60 → fail
4/5 = 80 → pass


Stage 1:

13 tasks
passingScore = 80

10/13 = 77 → fail
11/13 = 85 → pass


Stage 2:

12 tasks
passingScore = 80

9/12 = 75 → fail
10/12 = 83 → pass


R5 не должен изменять эти результаты.


============================================================
8. CURRENT COURSE AGGREGATION CONTRACT
============================================================

Общий progress:

numerator =
количество актуальных CourseLesson,
чей ID присутствует в completed IDs

denominator =
количество актуальных CourseLesson

fraction =
numerator / denominator

При пустом курсе:

fraction = 0
nextLesson = null

Home percentage:

round(fraction * 100)

nextLesson:

первый незавершённый урок в порядке:

module.order
→ lesson.order

Unknown/orphan persisted IDs:

не увеличивают numerator.

Denominator всегда определяется текущим content,
а не persistence.


============================================================
9. IDENTITY CONTRACT
============================================================

Текущая persistence identity:

lesson ID.

Module ID не входит в persisted identity.

На момент pre-R5 audit:

- все 22 lesson IDs глобально уникальны;
- IDs в lessons indexes соответствуют IDs полных lesson assets.

Поэтому текущая identity model допустима.

Не переходить на composite:

(moduleId, lessonId)

без отдельной причины.

Не менять lesson IDs в рамках R5.


============================================================
10. CONTENT EVOLUTION POLICY
============================================================

Текущая ожидаемая semantics:

новый lesson
→ увеличивает denominator
→ пользователь ещё не завершил его.

удалённый lesson
→ больше не участвует в denominator;
→ orphan persisted ID может остаться.

lesson перемещён между modules
→ completion сохраняется при сохранении ID.

изменён lesson ID
→ считается новым незавершённым уроком.

изменён passingScore/tasks
→ существующий completion сохраняется;
→ новая попытка использует новый content.

Сложные migrations в R5 не вводить.

Главная текущая политика:

lesson IDs должны быть стабильными и не переиспользоваться
для семантически другого урока.

18. R5.2 — SAVE / NAVIGATION CORRECTNESS
============================================================

Подтверждённые проблемы:

1. SharedPreferences write может вернуть false,
   но текущий UI всё равно может считать completion успешным.

2. Write может бросить exception,
   но пользователь не получает нормальный recoverable flow.

3. Completion save async.

4. Пользователь может попытаться уйти назад,
   пока запись ещё выполняется.

5. Repeated taps могут запустить несколько writes.

6. Parent refresh зависит от navigation result.

Цель:

completion считается persistent success
ТОЛЬКО после подтверждённого успешного save.


============================================================
19. R5.2 REQUIRED BEHAVIOR
============================================================

При нажатии completion:

IDLE
→ SAVING
→ SUCCESS

или:

IDLE
→ SAVING
→ ERROR


Во время SAVING:

- повторное нажатие completion не запускает вторую запись;
- UI явно показывает, что операция выполняется;
- нельзя случайно получить два successful pop;
- navigation lifecycle должен быть согласован с save.

SUCCESS:

- persistence подтверждена;
- только после этого возвращается successful navigation result.

ERROR:

- экран НЕ должен сообщать успешное completion;
- successful pop не выполняется;
- пользователь получает понятный feedback;
- должна быть возможность повторить сохранение.

Не требуется сложный state machine framework.
Достаточно локального Flutter state.


============================================================
20. R5.2 BACK DURING SAVE
============================================================

Отдельно решить существующую race:

completion save started
→ system back before save finished.

Предпочтительная semantics:

не позволять тихо уйти из completion flow,
пока результат persistence неизвестен.

Реализовать минимально средствами Flutter.

Не создавать глобальный navigation controller.

Проверить:

- delayed successful save;
- delayed failed save;
- system back;
- double tap;
- widget dispose;
- successful parent refresh.

34. R5.6 — SERIALIZE COMPLETION WRITES
============================================================

Подтверждённый API-level риск:

completeLesson использует read–modify–write.

Возможна последовательность:

A reads S
B reads S
A writes S + idA
B writes S + idB

и потеря idA.

Текущий обычный UX делает сценарий маловероятным,
но service contract должен быть надёжным.


============================================================
35. R5.6 REQUIRED BEHAVIOR
============================================================

Два concurrent completion requests
для разных lesson IDs:

completeLesson(A)
completeLesson(B)

после успешного завершения обоих должны сохранять:

A AND B.

Не создавать database transaction framework.

Использовать минимальный механизм сериализации writes
на уровне текущего persistence service.


============================================================
36. R5.6 MULTIPLE SERVICE INSTANCES
============================================================

Поэтому tests должны проверить фактический intended scope serialization.

Если простой instance-local queue НЕ защищает реальные production usage,
не считать проблему решённой.

Перед реализацией определить:

- сколько ProgressService instances реально создаётся;
- нужен ли shared/static serialization mechanism;
- можно ли проще централизовать существующий service instance.

Выбрать минимальное решение.


============================================================
37. R5.6 FAILURE RECOVERY
============================================================

Очередь/serialization mechanism не должна навсегда ломаться
после одного failed write.

Проверить:

A fails
→ B всё ещё может выполниться.

И:

A succeeds
→ B succeeds
→ оба ID сохранены.

Не превращать это в general-purpose async queue library.

Проверить текущий parser и определить минимальные invariants.

Сохранить compatibility с реальными assets.

Не менять valid current JSON.

Минимально рассмотреть:

- supported completion types;
- ordinary/default completion;
- quiz completion;
- passingScore requirement;
- passingScore range.

Malformed content должен fail clearly,
а не тихо создавать странную completion policy.


============================================================
40. R5.7 НЕ РАСШИРЯТЬ
============================================================

Не превращать R5.7 в полную schema-validation систему всего курса.

Не валидировать заново все LessonBlock types,
если это уже делает существующий parser.

Не вводить JSON Schema infrastructure.

Scope:
только LessonCompletion metadata.

============================================================
44. STOP CONDITIONS
============================================================

Агент ОБЯЗАН остановиться, если:

1. Требуется изменить persistent schema.

Например:

completed_lessons
→ сложные serialized completion objects.

2. Требуется решить, нужно ли сохранять:

- score;
- attempts;
- dates;
- simulator state;
- answers.

3. Требуется ввести backend/auth/cloud sync.

4. Возникает необходимость database.

5. Требуется repository/controller/use-case framework,
который существенно расширяет архитектуру.

6. Требуется изменить semantics:

«когда урок считается пройденным».

7. Требуется изменить quiz scoring formula.

8. Требуется изменить retry policy.

9. Требуется изменить passingScore реальных lessons.

10. Требуется изменить lesson IDs.

11. Требуется persistent reset policy.

12. Требуется module completion/unlocking policy.

13. Тесты и content задают противоречивые требования.

14. Fix одного R5.x начинает требовать существенного изменения
другого subsystem.

15. Baseline неожиданно ломается unrelated изменениями.

16. Для исправления storage race требуется архитектура,
существенно сложнее небольшого serialization mechanism.


============================================================
45. ПРИ STOP
============================================================

Сообщить:

1. текущий R5.x;
2. что обнаружено;
3. почему решение не следует принимать автоматически;
4. варианты;
5. рекомендуемый вариант;
6. последствия каждого варианта;
7. потенциально затрагиваемые файлы;
8. состояние tests/analyze/git.

Не выбирать product semantics самостоятельно.

47. UX ISSUES, КОТОРЫЕ НЕ НУЖНО ЧИНИТЬ СЛУЧАЙНО

  до persistent save;

Особенно:

НЕ равно

============================================================
49. R5 DEFINITION OF DONE
============================================================

R5 считается завершённым, если:

1. progress subsystem имеет прямое test coverage;

2. persistence schema остаётся простой и понятной;

3. false/exception при write не превращаются
   в ложное successful completion;

4. repeated completion tap не запускает несколько save flows;

5. navigation согласована с async persistence;

6. completion/scoring rules вынесены из Flutter State
   в небольшой pure Dart component;

7. существующие Stage 0/1/2 scoring contracts сохранены;

8. course aggregation является pure/testable calculation;

9. Home и Module имеют recoverable progress read error states;

10. concurrent completion writes не теряют разные IDs
    в поддерживаемом service usage;

11. malformed LessonCompletion metadata fail clearly;

12. session state не начал persist без product decision;

13. repository/use-case/controller framework не появился
    без необходимости;

14. SharedPreferences остаётся достаточным persistence mechanism;

15. flutter analyze clean;

16. flutter test полностью green;

17. git diff --check clean;

18. JSON/assets остаются неизменными,
    кроме случая отдельного явно согласованного content fix.

52. R5 EXIT DECISION
============================================================

READY допускается даже при наличии deferred P3/P4 issues,

- не приводят к потере прогресса в поддерживаемом flow;
- требуют нового product decision;
- являются будущими features;
- требуют migrations/versioning, которых пока нет.

NOT READY использовать, если остаётся подтверждённый P0/P1
в основном progress flow либо R5 изменил behavior без достаточного
regression coverage.
