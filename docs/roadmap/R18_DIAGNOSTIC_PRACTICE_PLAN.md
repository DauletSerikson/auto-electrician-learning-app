## 2. Образовательный контракт и границы

Отдельная точка входа «Практика диагноста», не `stage_14` и не набор обычных
теоретических уроков. Каталог из 18 кейсов не меняет знаменатель курса 132.
Входные знания рекомендуются, но автоматический unlocking не добавляется.

Цикл ученика: симптомы → конкурирующие гипотезы → цель проверки → безопасные
условия/точки → наблюдение → интерпретация → уточнение гипотез → обоснованный
вывод или признание недостаточности данных. Замена детали не считается проверкой.
Нельзя получить зачёт только по совпадению выбранного компонента с hidden truth.

Все сценарии полностью офлайн, синтетические и явно ограниченные схемой.
Никакого подключения к машине, Bluetooth, OBD-адаптера, backend, AI, аккаунтов
или универсального автомобильного solver. Числа этого плана — условия учебных
моделей, а не OEM-допуски. Схема, нагрузка, прибор и опора обязательны.
У кейса может быть корректный итог «недостаточно данных для компонента».

## 3. Архитектурное решение

Выбор: **ограниченный детерминированный сценарный движок**. Для каждой допустимой
комбинации `faultVariant + conditionProfile + action + parameters` определён
ровно один типизированный результат. Набор комбинаций конечен и проверяется
до показа кейса. Новый кейс с уже известными действиями добавляется данными.
Новый физический интерфейс/тип наблюдения требует отдельного расширения кода.

Поток данных:

```text
Bundled catalog/definition → strict parser/validator → PracticeDefinition
                                        ↓
Flutter PracticeController → pure Dart command reducer → PracticeAttempt
           ↓                         ↓                       ↓
       view models        ObservationEngine + FaultState   EvidenceRecord[]
           ↓                                                 ↓
     Flutter screens ← drafts/observations ← hypothesis claims + evaluator
```

Предлагаемые границы после отдельного разрешения реализации:

| Компонент | Ответственность, без лишних слоёв |
|---|---|
| `PracticeDefinition` | Immutable metadata, vehicle topology, условия, actions, hypotheses, conclusions, rubric, explanation |
| `FaultState` | Скрытый вариант неисправности и ограниченное состояние модели; неизменно в попытке |
| `ObservationEngine` | Pure Dart: проверка условий/безопасности, выбор одной outcome row, создание результата |
| `PracticeAttempt` / reducer | Pure Dart immutable состояние попытки и переходы по типизированным commands |
| `EvidenceRecord` | Immutable снимок наблюдения с условиями; история не зависит от текущего переключателя |
| `PracticeEvaluator` | Pure Dart оценка выбранного вывода, ссылок на evidence, интерпретаций, безопасности и маршрута |
| `PracticeController` | Небольшой Flutter ChangeNotifier, владеющий всей попыткой; UI только отправляет commands |
| `PracticeService` | Будущая загрузка bundled данных; отдельно от CourseService |
| `PracticeProgressService` | Только будущая опциональная запись результатов; не часть R18.1 и не часть engine |

Пример будущего размещения: `lib/practice/` с `definition`, `attempt`,
`observation`, `evaluation`; Flutter screens/widgets вне pure Dart файлов.
Не нужны абстрактные repositories на каждый тип и новый framework.
Использовать существующие тему, Material cards/buttons, ошибки загрузки/записи.
Не встраивать workflow в giant LessonBlock и не заменять LessonBlockRenderer.

Свойства детерминизма:

1. Нет random и зависимости результатов от wall clock. Intermittent задаётся
   объявленным окном готовой записи или индексом логического события.
2. Повтор одинаковой проверки в одном профиле даёт тот же результат; новая
   запись сохраняет свой ID, старую не перезаписывает. Повтор сам не даёт баллов.
3. Переход ON/OFF или выбор другого packet не исправляет неисправность.
   Ремонт не симулируется произвольной заменой компонента. Post-repair packet,
   если нужен, — отдельный подписанный учебный материал после оценки.
4. Отсутствие строки — ошибка definition, не 0 V и не «исправно».
   Валидное отсутствие знания задаётся `UnavailableObservation` с причиной
   `notModelled` / `notProvided` явно.
5. Parser/engine/evaluator не импортируют Flutter или shared_preferences.
   UI получает projection без hidden truth и answer keys. Офлайн assets можно
   изучить вне приложения: это учебная прозрачность, не защита экзамена от взлома.

## 4. Формат декларативных данных и строгая validation

Предлагаемый будущий каталог: `assets/practice/catalog.json`, case definitions
в `assets/practice/cases/`. На R18.1 этих файлов/директорий assets не создавать.
Ниже — спецификация внутри Markdown, а не production JSON.

| Поле definition | Содержание |
|---|---|
| `schemaVersion`, `id`, `contentRevision`, `rubricVersion` | Версии формата, контента и сопоставимости оценки; стабильный case ID |
| `title`, `difficulty`, `prerequisites`, `learningGoals` | Название по симптому, не по неисправной детали; ссылки на реальные module IDs |
| `vehicle`, `topology`, `points` | Система/тип датчика, источники, опоры, нагрузки, входные подтяжки, схемные узлы |
| `initialSymptoms`, `initialPacket` | Только выданные данные, timestamps, DTC status/source и ограничения |
| `faultVariants`, `selectedVariantId` | Авторские истинные состояния; стабильный default для пилота, без рандомизации |
| `conditionProfiles`, `transitions` | Конечные режимы: OFF, START, RUN, isolatedPacket; допустимые переходы |
| `actions`, `outcomes` | Действия, allowed parameters, predicates, safety class, полная таблица результатов |
| `hypotheses`, `claims`, `evidenceGroups` | Альтернативы, границы подтверждения/исключения, проверяемые доказательные наборы |
| `conclusions`, `assessmentGoal`, `rubric` | Подтверждённая область/insufficient/defer, обязательные критерии, веса |
| `feedback`, `retryPolicy`, `provenance` | Объяснения после отправки, reset current attempt, синтетика/источники |

Типизированные actions: `InspectDocument`, `SelectConditionProfile`,
`VoltageReading`, `CurrentCapture`, `IsolatedResistanceReport`, `ReadDtcPacket`,
`ReadLiveDataPacket`, `ReadTracePacket`, `RecordInterpretation`, `SubmitConclusion`.
Это конечный набор контракта, не список уже реализованных Dart subtype.
Точка/пара/режим выбираются только из объявленных ID; никакого произвольного кода.

Иллюстрация одной action/outcome пары будущего формата:

```json
{
  "action": {
    "id": "starter.contact_drop",
    "kind": "voltageReading",
    "mode": "dcVoltage",
    "redPoint": "Q",
    "blackPoint": "Kplus",
    "conditionProfile": "start_control_loaded",
    "safetyClass": "qualifiedProcedureOnly",
    "delivery": "preparedRecord",
    "purposeOptions": ["localize_control_loss", "prove_motor_healthy"]
  },
  "outcome": {
    "faultVariantId": "control_contact_high_r",
    "actionId": "starter.contact_drop",
    "conditionProfile": "start_control_loaded",
    "snapshotId": "ST-A",
    "result": {"kind": "numeric", "quantity": "voltage", "value": 7.56, "unit": "V", "resolution": 0.01}
  }
}
```

Пример не является полной definition. Все referenced IDs определяются полным
контрактом кейса; второй purpose не засчитывается, поскольку этот замер не
доказывает исправность мотора. Условия представлены enum/profile IDs, не текстовым
`eval`/Dart expressions. Ограниченная алгебра predicates: `allOf`, `anyOf`,
`not`, равенство enum/ID, интервалы чисел одной quantity/unit, ссылки на evidence.
Derived claims задаются именованными разрешёнными операциями (например,
разность двух voltage observations одного snapshot/reference), не скриптами.

Обязательные validation ошибки: неизвестные kind/schema/version/point/unit,
пустые обязательные значения, duplicate IDs, висячие ссылки, NaN/Infinity,
несовместимая quantity/unit, неоднозначные/пропущенные outcomes, недостижимая
обязательная группа, невозможный безопасный путь, unsafe action с delivery
physical, противоречие профилей/нагрузки/полярности, утечка solution в title.
Проверять граф переходов на достижимость и явно допустимые повторы;
циклы повторных измерений допустимы, автоматическое бесконечное продвижение — нет.

## 5. Истинное состояние, наблюдения и Evidence state

`FaultState` — описание конкретной ограниченной модели: например, один
контакт 180 Ω, один открытый путь S–E, фиксированная запись sleep.
В пилоте один дефект на вариант; несколько одновременных неисправностей
не подразумеваются. Конкурирующие гипотезы имеют объявленные predictions
для проверки различимости; это не обязательное равное число игровых вариантов.
Hidden truth известна автору/engine, но **не равна автоматически доказанному выводу**.

Семейство результатов, отдельные sealed subtype:

| Результат | Что означает |
|---|---|
| `NumericObservation` | value, quantity/unit, resolution/диапазон, red/black reference |
| `OpenLoopObservation` | Прибор не измерил проводимость в указанном диапазоне; не математическая бесконечность |
| `StatusObservation` | Enum: разрешение, valid/invalid, active/inactive, состояние подготовленного поля |
| `DataPacketObservation` | DTC/live data с источником, единицами, timestamps и признаком validity |
| `TraceObservation` | Готовая серия samples/оси/reference, режим прибора, частота дискретизации и окно |
| `UnavailableObservation` | Недостаточны/не предоставлены данные; причина, без фиктивного числового value |
| `BlockedAction` | Проверка запрещена или не выполнены условия; это событие, не измеренное 0 V |

Для любого замера: `U(red,black)=φ(red)−φ(black)`. Обратная полярность даёт
обратный знак, а не неверный физический результат; допустимость вывода
проверяет знак и выбранную опору. Неизвестный потенциал плавающей точки
помечается неизвестным. 0 V массы без нагрузки не доказывает низкое R под током.

`EvidenceRecord`: attempt ID, sequence, definition/content revision,
action/parameters, condition profile, snapshot/source packet ID, logical time,
снимок питания/нагрузки/команды/температуры/изоляции, raw typed result,
validity и safety decision. Смена профиля не меняет историю задним числом.
Из разных времён/режимов нельзя составить фиктивный синхронный снимок.
Timestamp источника, авторская метка учебного события и время чтения/приёма
packet — разные поля. Если реальный timestamp ECU не предоставлен, он unknown;
generic Freeze Frame не наделяется часами, а последовательное чтение PID —
вымышленным общим sample clock. Синхронность числовых примеров явно дана автором.
Invalid и blocked записи видны в журнале с причиной, но не закрывают proof group.

Общий `PracticeAttempt` содержит все selections и drafts: выбранные checks,
probe IDs, профиль, intent проверки, журнал, интерпретации с evidence IDs,
статусы гипотез, черновик вывода, финальную оценку, submission/save state.
State отдельных Flutter-карточек не является источником истины, даже если
они уничтожаются при lazy scroll. Контроллер создаётся один раз на route,
не в build; back из вложенного просмотра не создаёт новую попытку.

Commands: начать/выбрать профиль/запросить проверку/добавить интерпретацию/
пометить гипотезу/сформировать вывод/отправить/retry. После submit снимок
попытки frozen; экран оценки не меняет evidence. Retry создаёт новый attempt ID,
очищает только её drafts/results и возвращает исходный профиль/тот же вариант.
Completed/best других и текущего кейса не удаляются. История событий здесь —
учебный журнал, не внедрение инфраструктуры event sourcing.

## 6. Гипотезы, достаточность и итоговый вывод

Статусы, которые выбирает ученик: «не проверена», «поддерживается»,
«противоречит данным», «подтверждена в указанной области».
Каждое изменение ссылается на evidence и выбранную интерпретацию.
Evaluator проверяет raw records независимо от пометок ученика: выбор статуса
«подтверждена» не создаёт доказательство и не становится фактом модели.
Автоматически открывать диагноз или красить правильную гипотезу зелёным
после первого правильного замера нельзя. До submit показывать только запись
и условия; педагогическое объяснение причин ошибки — после общей оценки.

Proof group — одно обязательство: питание под нужной нагрузкой, локализация
потери, исключение альтернативы и т.п. Внутри группы могут быть альтернативные
доказательные наборы `anyOf(allOf(...), allOf(...))`. Порядок независимых проверок
не оценивается. Физические зависимости условий сохраняются: нельзя использовать
Ω питаемой цепи или вывести исправность проводов из ΔU при I=0.

`Conclusion` имеет область, тип и rationale:
- `ConfirmedFault`: подтверждённый участок/причина в границах модели;
- `InsufficientEvidence`: что известно, какие альтернативы остаются, какая
  следующая безопасная различающая проверка нужна;
- `ReferToQualifiedProcedure`: доказанный предел компетенции/данных и адресная
  передача, без приписывания конкретному компоненту неподтверждённого дефекта.

Два режима учебной цели:
1. `confirmable`: безопасно доступно достаточно данных. Раннее «недостаточно»
   правильно описывает текущее знание и может завершить попытку со статусом
   `needsMoreEvidence`, но не даёт mastery. Ученик получает указание на пробел,
   не автоматическое раскрытие неисправности.
2. `boundedDisposition`: доступные действия принципиально не разделяют
   несколько причин (обязателен кейс 18). Обоснованное «недостаточно + передать»
   может получить полный зачёт. Угадывание hidden truth — неверный уровень вывода.

Для второго режима автор обязан предъявить хотя бы пару гипотез, одинаково
объясняющих весь доступный packet, и доказать отсутствие разрешённой
различающей проверки. Иначе «недостаточно» превращается в удобный обход задания.
Сервисные детали, OEM pinout или qualification не генерируются догадкой.

## 7. Прозрачная модель оценки, отдельная от LessonAttempt

Предлагаемые для утверждения веса: диагноз D — 25, evidence E — 30,
интерпретация I — 25, безопасность S — 15, обоснованность маршрута R — 5.
`score = 25D + 30E + 25I + 15S + 5R`, все компоненты в [0,1].
Это отдельный `PracticeEvaluation`, без изменения scoring теоретического курса.
Вес evidence+interpretation 55% отражает цель практикума; минимальные 5%
маршрута не превращают хорошую диагностику в соревнование по скорости.

| Критерий | Проверяемая рубрика |
|---|---|
| D | 1 — максимально обоснованный допустимый вывод; 0.5 — верная более широкая область без ложной замены; 0 — неверный/чрезмерный вывод. Разрешённые уровни перечислены в definition |
| E | Доля выполненных обязательных proof groups; группы равны по весу в пилоте, alternative route не считается дополнительной группой |
| I | Доля корректных обязательных claims с валидными evidence IDs и условиями; «0 V под током» и «0 V при OFF» различаются |
| S | 1 — верно приняты обязательные safety decisions, нет подтверждённого опасного намерения; иначе 0 с конкретным объяснением |
| R | Доля уникальных проверок, для которых до выполнения выбрана обоснованная цель: различение остающихся гипотез, проверка условия/безопасности или контроль. Правильные intent заданы данными и текущим evidence |

Повторная одинаковая проверка не накручивает E/I/R и не штрафуется; чтение
схемы/возврат к журналу не считается лишним шагом. Повтор intermittent в новом
объявленном окне может быть необходимым. Нет штрафа за длительность, число
открытых экранов, перестановку независимых действий или иной допустимый путь.
Если не выполнено ни одной диагностической проверки, R=0; blocked actions
оцениваются S, не считаются полезными измерениями маршрута.

Mastery требует одновременно: D=1, все обязательные E groups, все critical I,
S=1 и score≥80 **до округления**. Число 80 — предлагаемая граница нового
практикума, а не импорт формулы quiz; её педагогическая калибровка — часть пилота.
Критические требования нельзя компенсировать баллами эффективности.
Правильное угадывание без evidence: D может быть 1, но E=0 и mastery=false.
Обоснованное ограничение вывода в кейсе 18: D/E/I/S могут быть 1, mastery=true.

Преждевременное предложение заменить компонент без нужного proof не мутирует
модель: сохраняется как решение ученика, теряется соответствующая E/I/D часть,
даётся объяснение «какой альтернативе пока не противоречат данные».
Произвольных −10/−20 за клик нет. Простое чтение описания запрещённого метода
не нарушение; только явное подтверждение опасного диагностического решения
фиксирует safety event и закрывает mastery этой попытки. Реальное опасное
действие движок никогда не выполняет. После разбора можно продолжить обучение,
затем пройти заново; требование безопасности объясняется до отправки решения.

Свободное текстовое обоснование можно сохранить в текущем draft для ученика,
но не оценивать «понимание текста» без AI. Оценка использует выбранные claims,
область вывода и ссылки на evidence, а не поиск ключевых слов.

## 8. Safety policy и матрица 18 кейсов

Классы действий для **каждого** кейса:
- **A, безопасное учебное:** анализ схемы/симптомов/готовых данных, выбор
  гипотезы, условий и точек на условной схеме, чтение журнала, ограничение вывода.
- **B, только процедура и квалификация:** реальный аналог проверки требует
  применимой OEM-процедуры/доступа/приборов/подготовки. В R18 доступен лишь
  подготовленный снимок/отчёт, помеченный как таковой. Нажатие в приложении
  не разрешает реальную работу и не раскрывает последовательность её выполнения.
- **C, запрещённое:** обход защит/блокировок, опасная подача питания, опасное
  подключение прибора. Исполнительного action нет; возможен лишь краткий
  вариант диагностического решения с объяснением запрета, без деталей выполнения.

Safety gate действует и в engine, не только в disabled button. Неизвестные
условия/квалификация не считаются выполненными. Для HV/SRS/тормозной гидравлики
только A-анализ готовых данных и передача специалисту: никаких точек подключения,
распиновок, измерения пиропатронов, управления клапанами/насосом/контакторами,
обхода HVIL, изоляционных испытаний, времени ожидания или HV disable sequence.
Обычное «выключено», нулевой PID или отсутствие лампы не означает безопасный HV.

Общие для всех паспортов: безопасные действия A из списка выше; B/C дополнительно
классифицированы ниже. **R0**: retry очищает всю текущую попытку/журнал/оценку,
возвращает тот же variant и профиль, не стирает сохранённые результаты.
После проверки explanation раскрывает причинную цепочку и границы знания;
до проверки финальный диагноз не показывается. Условия/значения синтетические.

### 8.1. Паспорта dp01–dp06

**dp01.** Автомобиль с разрешённым START, но без щелчка реле/прокрутки.
Гипотезы: недостаточное питание, запрет запуска, обрыв обмотки реле,
сопротивление контакта управления, механический отказ реле/дальнейшей цепи.
Действия/наблюдения/полный расчёт — §9: при START P=Q=12.60 V, K+=5.04 V,
Icoil=42 mA, ΔU контакта=7.56 V. Условия ST-A обязательны.
Допустим вывод о потере на контакте, не о моторе стартера. Критерии: питание,
разрешение, локализация под током, объяснение бесполезности ΔU при I=0.
B: реальные START/измерения; C: обход разрешений/перемыкание силовых выводов.
Объяснение: контакт ограничивает ток реле; retry R0.

**dp02.** Двигатель нормально прокручивается, ECU видит CMP, но нет CKP и RPM=0
в подготовленном capture. Hall CKP выбран трёхпроводным с питанием 5 V.
Конкурируют механическая синхронизация, CKP, питание/возврат, сигнал до ECU.
Истина — открыта ветвь питания CKP. В одном CRANK snapshot: источник reference
5.00 V, на питающем выводе CKP 0.00 V из-за объявленного локального pull-down,
возврат 0.00 V; capture сигнала не имеет фронтов. Это ещё не «датчик сломан».
Изолированный отчёт пути питания: OL (>20 MΩ); сигнальный провод 0.2 Ω,
путь возврата 0.2 Ω. Штатные питание/сигнальная нагрузка определены схемой.
Критерии: связать отсутствие сигнала с отсутствием питания, локализовать путь,
не выводить механическую неисправность из RPM=0. Вывод: обрыв питания CKP,
сам датчик и механика без проверки после восстановления не оценены.
B: реальные проверки при прокрутке/изоляция; C: обход запуска/питание неизвестных
контактов. Объяснение: работа ECU и CMP не доказывает питание CKP; retry R0.

**dp03.** После ночи АКБ разряжена, но причина не задана названием.
Обычная 12 V сеть: штатный sleep 0.03 A, отдельная лампа багажника 0.40 A.
Гипотезы: АКБ/SOH, постоянный потребитель, периодическое пробуждение, зарядка.
Истина — концевик удерживает лампу включённой. Доступны карта сети, готовая
запись тока и отчёты по ветвям: в объявленном settled-окне после 30 min 0.43 A;
после изоляции ветви по подготовленной процедуре и повторного sleep 0.03 A;
готовое наблюдение подтверждает свечение лампы при закрытом багажнике.
Открытие двери даёт профиль awake, его ток не участвует в сравнении sleep.
Критерии: одинаковые условия, локализация ветви, подтверждение потребителя;
нельзя объявить АКБ исправной по одному напряжению или обвинить вынутый F.
B: подключение реального измерителя/изоляция ветвей; C: амперметр поперёк АКБ.
Объяснение: 0.03+0.40=0.43 A, падение после ветви не доказывает неисправность F;
состояние АКБ требует отдельной оценки. Retry R0 сбрасывает логическое время.

**dp04.** При включении нагрузки зарядка на АКБ становится ниже ожидаемой.
Выбрана система с заданным ECU target=14.4 V, стабильным режимом и током
генератора в B+ ветви 40 A. Гипотезы: штатная стратегия, генератор/управление,
плюсовой путь, возврат, АКБ. Истина — 0.03 Ω одного B+ соединения.
Синхронно: вывод генератора относительно его G/N 14.4 V, P относительно N
13.2 V, падение на данном соединении 1.2 V, падение возврата 0.0 V в модели.
Другой prepared профиль без тока показывает 0 V на том же соединении.
Критерии: проверить requested/actual/нагрузку, связать ΔU=I·R,
не приписать изменение «умной зарядке» без проверки target.
Вывод: подтверждён участок B+, не общая замена генератора/АКБ.
B: измерения около работающего привода; C: отключение АКБ при работающем моторе.
Объяснение: 40×0.03=1.2 V только в указанной ветви; retry R0.

**dp05.** Одна условная лампа светит слабее, соседняя исправна.
Модель: идеальный источник 12 V, лампа как фиксированные 5 Ω (без тепловой
динамики), дефектный плюсовой контакт 1 Ω, идеальный возврат.
Гипотезы: питание, лампа, плюсовой контакт, масса. Под LOAD: I=2 A,
Uлампы=10 V, ΔUконтакта=2 V, ΔUвозврата=0 V. При OFF ток 0, потеря 0.
Доступны выбор точек V DC и готовые данные тока. Критерии: доказать локальную
потерю под током и не признать контакт исправным по OFF-кадру.
Вывод: высокое сопротивление плюсового контакта; R=2/2=1 Ω в модели,
не норматив любого автомобиля. B: реальное подключение к цепи; C: увеличение F/
шунтирование контакта. Объяснение — деление напряжения 12=2+10; retry R0.

**dp06.** Штатный предохранитель повторно открывается; новая установка не предлагается.
12 V ветвь разделена на два участка, потребитель изолирован в готовом OFF-отчёте.
Гипотезы: перегрузка потребителя, провод на кузов, ошибочный номинал,
межцепное замыкание. Истина — повреждённый провод участка W2 касается кузова.
W2–N=0.2 Ω при изолированных концах, W1–N и отключённый потребитель–N >20 MΩ;
документированный осмотр показывает место повреждения изоляции W2.
Критерии: указать изоляцию/отсутствие параллельных путей, отделить локализацию
от предположения «некачественный F», не подавать питание для повторного опыта.
Вывод: замыкание W2 на кузов в условиях модели; номинал F не меняется.
B: реальная изоляция/осмотр/омметр; C: повышенный номинал, многократная подача
питания на известное замыкание. Объяснение — защита реагирует на причину; retry R0.

### 8.2. Паспорта dp07–dp12

**dp07.** Нагрузка работает нестабильно, точка «массы» при OFF имеет 0 V.
Источник 12 V, нагрузка 5 Ω, возвратный контакт 1 Ω; истинно high-R возврата.
Гипотезы: слабый источник, плюсовая потеря, возврат, нагрузка.
При LOAD: I=2 A, U(плюс,N)=12 V, U(минус нагрузки,N)=2 V,
Uнагрузки=10 V; OFF: I=0, потенциал возврата 0 V.
Действия — сравнить профили, прямое падение возврата или синхронную пару
потенциалов. Критерии: нагрузочный proof, полярность, разграничение потенциала
и сопротивления. Вывод: потеря на указанном возвратном контакте, не «вся масса
автомобиля плохая». B: реальные измерения под током; C: обход защит/случайная
перемычка. Объяснение — 2 A×1 Ω=2 V; retry R0.

**dp08.** Иногда пропадает отклик аналогового датчика, DTC может быть историческим.
Низкоомный выход датчика 2.5 V, ECU input имеет заданный pull-down; источник/
возврат исправны. Гипотезы: датчик, питание, возврат, сигнальный путь, ECU.
Истина — периодически открывается участок S–E. Готовое синхронное окно A:
S=E=2.5 V; окно B при одном логическом событии: S=2.5 V, E=0 V,
питание остаётся 5 V, возврат 0 V. Отдельный подготовленный отчёт подтверждает
потерю проводимости S–E в том же событии. Одиночный хороший замер недостаточен.
Критерии: выбрать окно отказа, сохранить timestamps, локализовать путь,
не смешать «раньше» и «сейчас». Вывод: intermittent сигнального пути;
конкретный вид повреждения без осмотра не доказан.
B: реальная проверка жгута/осциллограф; C: замыкание/питание неизвестного сигнала.
Объяснение — источник сигнала сохраняется по одну сторону разрыва; retry R0,
события воспроизводятся с теми же индексами, не случайным таймером.

**dp09.** Одна дверь не запирается, остальные сработали. Объявлен отдельный
канал BCM H-bridge к мотору A/B, LOCK: выход A=12 V, B=0 V.
Гипотезы: запрос/разрешение, драйвер, проводка, мотор/механика.
Истина — открыт A-провод между выходом и мотором. Под LOCK:
на выходе BCM 12/0 V, на моторе 0/0 V (A стянут к B через обмотку), I=0;
изолированный A-путь OL, B-путь 0.2 Ω, обмотка конечного известного R.
Критерии: сравнить два конца пути и напряжение именно A–B, не два произвольных
«плюса относительно кузова». Вывод: открыт A-путь, исправность всех механических
элементов ещё не гарантируется. B: реальный доступ к двери/движущемуся замку;
C: внешнее питание неизвестных выводов. Объяснение — другие двери не доказывают
исправность данного канала; retry R0.

**dp10.** Стекло движется вниз, запрос вверх не выполняется. Модель:
дверной модуль с UP-входом, pull-up 5 V, кнопка замыкает его на G.
Гипотезы: UP-контакт, провод входа, anti-pinch/разрешение, H-bridge, механика.
Истина — контакт UP остаётся разомкнут. Prepared data: питание модуля штатное,
запретов нет, UP на входе остаётся 5 V при запросе, DOWN распознаётся;
изолированный UP-провод 0.2 Ω, контакт UP в нажатом положении OL,
DOWN-контакт в нажатом положении 0.2 Ω. Движение вниз само по себе не доказывает
исправность драйвера вверх. Критерии: проследить input→command→output и
различить кнопку/провод; вывод: открытый UP-контакт переключателя.
B: реальное движение стекла/изоляция; C: отключение anti-pinch/обход защиты.
Объяснение — модуль не получает запрос, а не автоматически «сгорел BCM»; retry R0.

**dp11.** Дворники не начинают запрошенный цикл. Это конкретная BCM-архитектура:
пуск допускается только при valid park-feedback, не общее правило дворников.
Гипотезы: запрос/сеть, питание мотора, park-датчик/путь, BCM.
Истина — открыт park-путь. Packet: запрос принят, питание BCM исправно,
отказ команды подписан `park_feedback_invalid`; отдельная подготовленная
стендовая запись выхода park-источника переключается 0/5 V, вход BCM
неизменно 5 V через pull-up; это не замеры неподвижного и вращающегося механизма
в один момент;
изолированный путь между ними OL. Мотор не запитан — его исправность неизвестна.
Критерии: различить принятие запроса и выдачу команды, источник/доставку feedback,
не диагностировать мотор по отсутствию движения. Вывод: обрыв park-пути;
последующий контроль механики требует отдельной процедуры.
B: доступ к движущимся механизмам/цепи; C: принудительный обход park/защиты.
Объяснение — отказ разрешения вызван отсутствием достоверного входа; retry R0.

**dp12.** Отопитель работает только на максимальной скорости. Выбрана классическая
резисторная схема, не PWM-controller: low/medium проходят термозащиту,
high обходится штатной отдельной ветвью. Истина — термозащита открыта.
Гипотезы: переключатель, термозащита/резисторы, проводка, мотор, ограничения HVAC.
Подготовленные данные: low request принят, 12 V до термозащиты и 0 V после
(через выбранную пассивную нагрузку к N); high даёт 12 V на моторе и движение.
OFF/isolation: термозащита OL, секции резистора 0.4/0.8 Ω, проводники 0.2 Ω.
Критерии: локализация открытой защиты, различие топологий, предел знания.
Вывод: открыт защитный элемент низких скоростей; причина перегрева не установлена,
замены «и готово» недостаточно. Следующие вопросы — ток/воздушный поток по
подготовленной процедуре, без обхода защиты.
B: реальная проверка горячих/движущихся частей; C: шунт термозащиты.
Объяснение — подтверждён отказ цепи, но не устранена первопричина; retry R0.

### 8.3. Паспорта dp13–dp18

**dp13.** MIL и P0102; это сообщение о тракте, не название сломанной детали.
Выбран аналоговый MAF, а не частотный/цифровой. Гипотезы: питание/возврат,
MAF, обрыв/замыкание сигнала, вход ECU. Истина — открыт S–E.
Полный пакет, измерения, proof sets, вывод и варианты недостаточности — §10.
Критерии: DTC≠причина, сопоставление двух концов при одинаковом режиме,
изолированный контроль пути, ограничение диагноза. B: реальные измерения/изоляция
электроники; C: подача питания в сигнальный вход/замена без evidence.
Объяснение: sensor-side signal существует, ECU-side signal отсутствует;
открытый путь подтверждён отдельно, не одним кодом. Retry R0.

**dp14.** В готовой записи ABS одна скорость периодически недостоверна.
Одинаковые колёса, прямолинейный эквивалент стенда; активный датчик и энкодер
48 пар полюсов. При 250 rpm исправный канал 200 Hz, один оборот 0.24 s.
Истина — повреждение одного сектора энкодера. Гипотезы: питание/проводка,
датчик, энкодер/зазор, валидность скорости, блок ABS.
Синхронные prepared captures: стабильное питание/возврат; пропуск события
повторяется раз в 0.24 s именно в одном угловом секторе; готовый сравнительный
отчёт с проверенным датчиком сохраняет секторный дефект, отчёт осмотра
подтверждает повреждение энкодера. Один Live Data провал не определяет компонент.
Критерии: временная/угловая связь и проверка альтернатив, не замена ABS ECU.
Вывод: дефект области энкодера в рамках packet; до последних отчётов — данных мало.
A: только готовые записи; B: реальные работы с колесом/датчиком только специалист;
C: гидравлика/активация тормозов/опасный дорожный опыт. Объяснение — periodic
local defect не тождественен DTC конкретной детали; retry R0.

**dp15.** Сканер сообщает потерю связи с одним ECU. Известны gateway, сегмент CAN,
отдельная защищённая ветвь питания и возврат. Истина — открыт путь Fout→ECU P.
Гипотезы: не тот адрес/режим/инструмент, питание/возврат, сегмент/ответвление,
сам блок. В packet другие узлы обмениваются кадрами, Fout=12 V, ECU P=0 V
при заданной входной нагрузке к N, возврат подтверждён отдельным нагрузочным
отчётом; изолированный питающий путь OL. Сеть не признаётся полностью исправной
только потому, что работают другие ECU или измерены условные 60 Ω.
Критерии: питание перед обвинением CAN/ECU, локализация, условия измерения.
Вывод: открыт путь питания блока, способность его к обмену после восстановления
требует контроля. B: реальные проверки питания/шины; C: перемычки CAN/подача
питания в DLC/неизвестный pin. Объяснение — no communication не равно ECU failed;
retry R0.

**dp16.** Форма Hall-сигнала выглядит неправдоподобно. Гипотезы: датчик,
возврат/проводка, штатная геометрия, режим прибора. Истина — исходная запись
сделана с AC coupling. Источник даёт 0–5 V square, 100 Hz, 50%; DC capture
показывает эти уровни. В AC packet выбран идеальный high-pass первого порядка,
τ=20 ms, установившийся режим: каждые 5 ms сигнал скачет между ветвями;
положительная полуволна спадает от +2.811 до +2.189 V, отрицательная
от −2.811 до −2.189 V. DC-составляющая утрачена, а источник не менялся.
Оба packet содержат одинаковые rpm/точки и metadata, отдельная подготовленная
запись опорного сигнала подтверждает настройку прибора. AC waveform — готовые
samples с объявленной моделью входного фильтра, не новая функция ScopeSignal.
Критерии: сначала проверить measurement chain; вывод: исходная форма искажена
настройкой измерения, по ней нельзя заменять датчик. Полная исправность датчика
во всех режимах не доказана. A: сравнение metadata/trace; B: реальное подключение
осциллографа; C: неизвестная земля прибора/подключение к HV или пироцепям.
Объяснение — качество наблюдения и дефект объекта различаются; retry R0.

**dp17.** BEV не начинает AC-зарядку. Внутренняя HV-схема и отрицательный HV
полюс не приравниваются к кузову; доступны только подготовленные сообщения.
Гипотезы: внешнее разрешение EVSE, сетевая доступность, LV, разрешение автомобиля,
OBC/HV-система. Истина — внешняя авторизация EVSE отклонена.
Общий timestamp: LV ready по предоставленному статусу, запрос автомобиля принят,
EVSE `authorization_rejected`, power delivery not permitted. По одному
`charging=false` данных мало; после EVSE packet допустим вывод «сессия не
разрешена внешней авторизацией», а не «все HV-компоненты исправны».
Критерии: разделить внешний/внутренний контекст, не приписывать no charge отказу
тяговой батареи, безопасно передать вопрос оператору/квалифицированному сервису.
A: только prepared status/document analysis; B: реальные электрические работы
за границей приложения; C: HVIL/contactors/вскрытие/обход разрешений/EVSE mains.
Объяснение — установлено условие блокировки, не полная исправность HV; retry R0.

**dp18.** Лампа SRS и подготовленное сообщение «сопротивление цепи выше
допустимого» для названной OEM-системы, без выдачи выводов/номиналов пироцепи.
Истинный fault state автора — плохой контакт цепи преднатяжителя. Те же
доступные сообщения могут быть объяснены проводкой, контактом, исполнительным
элементом или измерительным трактом ECU; distinguishing packet не предоставлен.
Доступны статус/контекст DTC и сервисное описание границы компетенции.
Они локализуют отмеченную системой цепь, но не подтверждают конкретную деталь.
Критерии mastery: перечислить сохраняющиеся альтернативы, доказать предел
доступных данных, отказаться от замены/сброса ради лампы, передать по OEM-процедуре.
Допустимый полный итог: `InsufficientEvidence + ReferToQualifiedProcedure`.
A: только сообщения/анализ; B: реальная диагностика SRS исключительно специалистом,
без предоставления её шагов; C: омметр/лампа/питание пироцепи, обманка, crash reset.
Объяснение — знание автором дефекта не делает его доказуемым для ученика;
retry R0 не открывает дополнительные опасные действия.

## 9. Полностью проработанный пример: dp01, цепь стартера

### 9.1. Что видит ученик и что знает модель

Карточка: обычный 12 V автомобиль, START запрошен, двигатель не вращается,
щелчок промежуточного реле не слышен. Нет подсказки «неисправный контакт».
Предоставлена функциональная схема без реальных OEM pin numbers:

```text
P (12.60 V относительно N) → разрешённый управляющий ключ → Q
Q → контакт C → Kplus → обмотка K1 (120 Ω) → Kminus=N
контакт K1 → команда S50 → условная цепь втягивающего → силовая ветвь мотора
```

В ST-A управляющий ключ идеален и замкнут, возврат Kminus–N идеален,
обмотка K1=120 Ω, её условное напряжение втягивания ≥8.0 V.
Истинно **C=180 Ω**, остальные перечисленные части управления исправны.
Это параметры именно учебного промежуточного реле, не катушки втягивающего
реального стартера. Силовая ветвь мотора не описывается этим сопротивлением.
Источник идеален в этом кадре; динамическая модель АКБ/стартера не вводится.

Причинность: `C=180 Ω → Icoil=12.60/(180+120)=0.042 A →
Ucoil=5.04 V < 8.0 V → K1 не втягивается → команда S50 отсутствует →
ток мотора 0 → нет прокрутки`. ΔU(C)=0.042×180=7.56 V.
S50=0 в модели благодаря объявленному пассивному пути на N, не из предположения
«любая неподключённая точка равна 0». Основной мотор не оценивается исправным.

### 9.2. Доступные действия и результаты

Все START/Ω/current результаты — готовые specialist records с выбором точки
на условной схеме; нет физического запуска/подключения. B→prepared delivery.

| ID | Условия и точки | Наблюдение истинного варианта | Что допустимо / чего не доказывает |
|---|---|---|---|
| ST0 | Документ схемы и разрешений | Условная схема, START permit=true | Разрешение есть в этом кадре, не универсальный алгоритм запуска |
| ST1 | ST-A START, V DC red P / black N | +12.60 V | Питание управляющей ветви доступно; SOH/CCA АКБ под током мотора не доказаны |
| ST2 | ST-A, red Q / black N | +12.60 V | До C напряжение доставлено |
| ST3 | ST-A, red Kplus / black N | +5.04 V | Узел после C ниже; отдельно не отличает потерю плюса от всех иных моделей |
| ST4 | ST-A, red Kminus / black N | 0.00 V | Возврат обмотки без потери при Icoil, не проверка массы под стартерным током |
| ST5 | ST-A, синхронный ток обмотки K1 | +42 mA, направление Q→K1→N | Ток не нулевой; это не ток силового мотора |
| ST6 | ST-A, red Q / black Kplus | +7.56 V | Потеря на конкретном C под током |
| ST7 | ST-A, ток мотора и main cable drop | 0 A и 0 V | При I=0 нельзя подтвердить исправность силового кабеля |
| ST8 | ST-OFF, ключ открыт, ток 0 | ΔU(C)=0 V | Этот кадр не исключает C=180 Ω |
| ST9 | Prepared isolated report C, питание исключено, участок изолирован | 180 Ω | Подтверждает C в условиях отчёта, но не заменяет объяснение отказа под током |

Обратные щупы ST6 дают −7.56 V: результат физически корректен. Правильно
прочитанная обратная полярность допускается как доказательство той же потери.
Разность ST2−ST3 допускается только как данные одного ST-A и общей опоры N.

### 9.3. Конкурирующие гипотезы и различение

Контрфактические значения — отдельные объявленные состояния того же условного
контура, не генератор неисправностей всего автомобиля. Числа относятся к
моменту запроса START; для запрета ключ открыт.

| Гипотеза | P / Q / Kplus / Kminus, V | Icoil | Отличие от наблюдаемого |
|---|---|---:|---|
| Недостаточное питание управления, источник 6 V | 6 / 6 / 6 / 0 | 50 mA | Нет 12.60 V на P/Q |
| Запуск не разрешён | 12.60 / 0 / 0 / 0 | 0 | Permit=false и Q=0 |
| Обмотка K1 разомкнута, C исправен | 12.60 / 12.60 / 12.60 / 0 | 0 | Нет тока/нет падения на C |
| Истинно: C=180 Ω | 12.60 / 12.60 / 5.04 / 0 | 42 mA | Совпадают ST1–ST6 |
| Высокое R возврата 180 Ω, C исправен | 12.60 / 12.60 / 12.60 / 7.56 | 42 mA | Потеря в возврате, а не на C |
| Механический отказ K1, C исправен | 12.60 / 12.60 / 12.60 / 0 | 105 mA | Обмотка получает полное напряжение, это другой pattern |

Главная силовая цепь тоже может объяснить отсутствие прокрутки, но не
объясняет одновременно пониженное питание обмотки и ST6. Подтверждение C
не доказывает отсутствие дополнительных неисправностей реального автомобиля;
один дефект — явно объявленная граница учебного варианта.

### 9.4. Evidence, допустимый диагноз, оценка и retry

Обязательные proof groups:
1. Контекст управления: схема, разрешение START и ST1 при текущем запросе.
2. Локализация потери: `ST5 + ST6 + ST4` **либо**
   `ST5 + ST2 + ST3 + ST4` одного ST-A.
3. Подтверждение именно высокого сопротивления: согласованный ΔU/I на C
   **либо** ST9 с объяснением связи с нагрузочным кадром, а не один OFF Ω.

Critical interpretations: Icoil≠I_motor; 0 V при I_motor=0 не означает
исправность силового пути; низкое Ucoil обусловлено конкретной потерей;
питание управляющей ветви не является испытанием АКБ под стартерной нагрузкой.
ST6 допустимо получить до ST1, если профиль уже выбран: порядок не штрафуется.

Полный допустимый вывод: «В данной модели повышено сопротивление контакта C
цепи управления K1; падение под током не позволяет реле втянуться. Дефект
самого стартера и состояние силового пути из этих данных не установлены».
Преждевременное «заменить стартер», «АКБ точно исправна» или «поставить
перемычку» не удовлетворяет рубрике. Из одних симптомов корректно сказать
«недостаточно», назвать альтернативы и следующую проверку, но mastery пока нет.

Все proof groups/critical claims/безопасность/вывод и обоснованные intent
дают 100. Угаданный C без доказательств не проходит E gate даже при D=1.
Правильный результат замера с неверным смыслом не закрывает critical I.
После submit показывается цепочка расчёта выше и индивидуальные пробелы.
Retry R0 возвращает неизменный C=180 Ω и исходный OFF-профиль без старых ответов.

## 10. Полностью проработанный пример: dp13, P0102

### 10.1. Функциональная схема и исходный packet

Автомобиль: учебный бензиновый двигатель с **аналоговым** MAF, ECU и
независимым питанием датчика P=12.60 V относительно N, возвратом G=N.
MAF имеет функциональный выход S; вход ECU E подтянут к N резистором 100 kΩ.
Внутренний источник MAF в выбранном прогретом idle-профиле равен 1.600 V
относительно G и имеет последовательное выходное сопротивление 1 kΩ.
Сигнальный путь S–E в исправной модели имеет пренебрежимо малое R.
Это условные функциональные обозначения, не pinout реального автомобиля.

Правильный сигнал при соединённом пути:
`U(S,N)=U(E,N)=1.600×100/(100+1)=1.58416… V`.
Истинная неисправность — **разомкнут сигнальный путь S–E**, поэтому S=1.600 V
без нагрузки входа, а E=0 V через объявленный pull-down 100 kΩ.
Питание и возврат MAF остаются исправны. Числа не переносятся на другой MAF:
существуют частотные/цифровые интерфейсы и иные bias circuits.

Исходные данные: MIL, stored/confirmed P0102, исторический freeze frame с
авторской меткой события/режимом (clock ECU неизвестен) и готовые текущие
записи RUN-A. Статус confirmed сам не доказывает,
что неисправность активна сейчас, и не определяет компонент. Смысл P0102 —
низкий вход MAF-тракта, а не разрешение замены датчика [S1, S2 в §17].
В учебном пакете отдельно дан raw ECU-input voltage=0.000 V; это подготовленный
инженерный канал, **не обещание стандартного OBD PID для каждого автомобиля**.
Calculated mass flow/fail-safe value нельзя выдавать за прямое напряжение входа.

### 10.2. Действия, условия, результаты и пределы

| ID | Условие/действие | Истинный результат | Разрешённое следствие |
|---|---|---|---|
| MF0 | Прочитать DTC, status, FF, тип интерфейса и схему | P0102; аналоговый MAF, bias E→N 100 kΩ | Выбрать гипотезы; окончательной причины нет |
| MF1 | RUN-A, цепь подключена, датчик в штатном рабочем режиме; red P / black G | +12.60 V | Питание на датчике есть в этом режиме |
| MF2 | RUN-A, red G / black N; штатная нагрузка датчика присутствует | 0.000 V при объявленном токе питания MAF 50 mA | Потеря возврата не объясняет этот кадр; это не проверка любой массы под любым током |
| MF3 | RUN-A, red S / black G, высокоомный канал записи | +1.600 V | Выход на стороне MAF существует |
| MF4 | RUN-A, red E / black N, тот же capture group | 0.000 V | ECU-side значение отличается; по одному MF4 нельзя отличить все причины |
| MF5 | RUN-A, независимый raw-input packet ECU | 0.000 V, valid | Согласуется с внешним E; не доказывает исправность ECU во всех режимах |

| MF7 | Тот же ISOLATED-PACKET, обе стороны сигнального жгута относительно N | >20 MΩ с обеих сторон | У подготовленного изолированного жгута не найдено замыкание на N в этом диапазоне |
| MF8 | Альтернативный prepared sectional report J1–J2 и исправных подводов | J1–J2 OL; подводы S–J1 и J2–E по 0.2 Ω, связь с N >20 MΩ | Более узкая локализация внутри того же сигнального пути |
| MF9 | Только исторический FF либо отсутствует питание/тип датчика/условия | Явно «данных недостаточно» для текущей причины | Запросить применимый пакет, не подставлять 0 V/MAF failed |

MF1–MF4 относятся к **одному** RUN-A, а MF6–MF8 — к отдельному
подготовленному состоянию изоляции. Их нельзя выдать за одновременную запись
работающего двигателя. Омметр в RUN блокируется, записи измерения не создаёт.
Реальные disconnect/connect/запуск здесь не исполняются и не инструктируются.
Показания RUN округлены как явно идеализированный high-impedance capture;
влияние конечного входного R реального DMM не переносится в модель молча.

### 10.3. Проверка альтернатив

| Гипотеза | Что ожидается в объявленной модели | Что её различает |
|---|---|---|
| MAF сам выдаёт 0 V при исправной линии | S и E около 0 при сохранном питании; S–E проводит | MF3=1.600 и MF6=OL этому противоречат |
| Нет питания MAF | MF1 не соответствует рабочему питанию; выход без дополнительной модели не предсказываем | MF1/MF2 проверяют условия, не диагноз по default value |
| Неисправен возврат | Другой G−N под нагрузкой; сравнение S относительно G и E относительно N требует учёта смещения | MF2 и профиль нагрузки |
| Сигнальный путь замкнут на N | При целой линии оба конца низкие; например, short 10 Ω вместе с 1 kΩ выхода даёт около 0.016 V | Высокий MF3 и изолированный MF7 не соответствуют этой альтернативе |
| Истинно: разомкнут S–E | S=1.600, E=0 через pull-down; изолированный S–E >20 MΩ | Совпадают пространственное разделение и MF6/MF8 |
| Вход ECU удерживает линию низко | При целом пути должен нагрузить и S; после изоляции жгут проводит, внутренний дефект ECU исключён из его Ω-отчёта | MF3 и MF6; один DTC этого не различает |

При неизвестном типе сигнала/подтяжке нельзя универсально объявлять обрыв
по 0 V: в другом ECU разрыв может дать высокое/плавающее значение.
Если разрешены только DTC и MF4, несколько гипотез остаются; правильный
промежуточный итог — недостаточно данных, следующая цель — питание/возврат,
сопоставление сторон и применимый prepared isolation report.

### 10.4. Proof sets и окончательная оценка

Обязательные группы:
1. MF0: верно определён интерфейс/контекст кода; FF не выдан за текущий замер.
2. MF1+MF2: питание и возврат проверены в рабочем режиме.
3. MF3+MF4 одного RUN-A: локализовано различие по сторонам пути,
   с учётом разных reference IDs; G=N подтверждено MF2.
4. `MF6+MF7` **либо** MF8 с полной декларацией изоляции/целых подводов.

MF5 полезен как проверка согласованности и может иметь обоснованный intent,
но не обязателен при достаточных независимых данных. Все проверки можно
выполнить в любом порядке в рамках валидных профилей; постоянный fault variant
позволяет разные prepared packets без требования единственной последовательности.

Critical claims: DTC≠компонент; сигнал S и вход E не одно наблюдение;
условия Ω и RUN различны; OL — предел диапазона; подтверждён **путь**, а
физическая природа «провод/контакт» без дополнительного отчёта не установлена.

Полный допустимый вывод: «В учебной модели практически разомкнут сигнальный
путь S–E: выход MAF присутствует, вход ECU удерживается pull-down около нуля,
подготовленный изолированный отчёт подтверждает отсутствие проводимости пути.
Это объясняет низкий вход. Замена MAF/ECU не обоснована. После восстановления
пути потребуется проверка сигнала/монитора по применимой процедуре».
MF8 допускает уточнение до J1–J2. Причина износа/коррозии без осмотра неизвестна.

Совпадение с hidden fault без четырёх evidence groups не даёт mastery.
Интерпретация «0 V — значит точно ECU/MAF» не проходит critical I.
Если MF6/MF8 отсутствует, допустима лишь более широкая локализация потери
между сторонами, с необходимостью следующей проверки; не полный зачёт dp13.
После submit раскрывается причинная цепочка, ошибка и недостающие условия.
R0 очищает попытку и возвращает тот же открытый путь; completed/best не стирает.

## 11. UX без потери состояния и лишней сложности

Навигационная схема будущей реализации:

```text
Home → «Практика диагноста» → Каталог → Карточка сценария → Начать попытку
  → Рабочий экран [Проверки | Журнал | Гипотезы]
      → Просмотр результата выбранной проверки → назад к той же попытке
      → Итоговый вывод + evidence links → Отправить заключение
          → Оценивание → Сохранить результат / Повторить попытку
```

| Экран/состояние | Минимальный полезный UX |
|---|---|
| Каталог | Симптомные названия, сложность, навыки, отдельные practice completion badges; без diagnosis spoiler |
| Карточка | Машина/архитектура, симптомы, ограничения, предзнания, цель навыка; кнопка начала |
| Проверки | Список с целью, текущими условиями, статусом доступности; недоступность объясняется текстом |
| Выбор условия/точек | Только объявленные варианты, видимая полярность/опора и нагрузка; draft хранится в контроллере |
| Наблюдение | Raw значение/единица/условия/дата packet; явно неизвестно/недоступно; никаких «верный диагноз!» |
| Журнал | Последовательность неизменных записей; фильтр по профилю, раскрытие условий; ссылки на evidence |
| Гипотезы | Несколько альтернатив, статус/обоснование ученика; не автоматическое решение двигателем |
| Итог | Область вывода, подтверждённый дефект/недостаточно/передача; обязательные claims и выбранные записи |
| Оценивание | Пять критериев отдельно, обязательные пробелы, safety, объяснение, границы диагноза; одна общая отправка |
| Retry | Явный полный reset только текущей попытки; сохранённый лучший/завершённый результат остаётся |

После submit все диагностические controls/клавиатурный ввод frozen,
журнал доступен для чтения. Одновременная повторная отправка/сохранение
блокируется; ошибка записи сохраняет frozen результат и даёт retry записи,
не заставляет заново проходить кейс. Оценка по каждой карточке не отправляется.

360 logical px: одна колонка, без обязательной боковой панели/широкой таблицы;
длинные подписи переносятся, кнопки/поля без фиксированной высоты.
Для условий и ID точек — Wrap/вертикальные списки, для trace — подписанные
оси и текстовое summary, возможность открыть график отдельно, без tiny hotspots.
План тестов: TextScaler 1.0/1.3/2.0, portrait/landscape, keyboard inset,
TalkBack/focus order, смысловые labels/selected/disabled reasons, различие
не только цветом, touch targets не менее 48 logical px.

ListView может удалять любые карточки: восстановление selections/evidence
идёт из PracticeAttempt, не из widget-local State, TextEditingController или
keep-alive. Только локальные анимации/раскрытие незначимых подсказок допустимы
в State. Обновление текста/размера, смена вкладки и просмотр записи сохраняют
draft. Выход из незавершённой попытки предупреждает о потере session; это
не обещание восстановления после убийства процесса до утверждения persistence.

## 12. Persistence: анализ и минимальное предложение, без реализации

В R18.1 **ничего не менять** в storage, ProgressService, pubspec и schema.
Будущий practice result не попадает в `completed_lessons` и не влияет на
вычисление course progress. Не считать совпадение case ID и lesson ID допустимым.

| Данные | Решение для предлагаемого пилота | Причина |
|---|---|---|
| Выполненные кейсы | После отдельного утверждения — сохранять при явном «Сохранить результат» и mastery | Полезно видеть завершённое, нет автозаписи за просто открытый кейс |
| Лучший результат | Сохранять вместе с revision/rubric, сравнивать только сопоставимые записи | Понятная обратная связь; безопасность/обязательные gates важнее голого score |
| История всех попыток | Отложить; не нужна для первого обучающего цикла | Неограниченный журнал не нужен в shared_preferences |
| Незавершённая попытка | Только route-memory, потеря при закрытии явно объяснена | Не нужна сложная сериализация transient state на первом пилоте |

Минимальное будущее хранение: **один новый** key `diagnostic_practice_progress_v1`,
один JSON envelope `schemaVersion + casesById`; внутри case ID —
`bestByAssessmentRevision`, ключ которого связывает contentRevision/rubricVersion.
В каждом таком record — mastery kind (`none`/`confirmed`/`justifiedReferral`),
best total и пять criterion scores, при необходимости confirmed completion timestamp.
Незачтённый результат тоже можно явно сохранить как best, но он не завершает кейс.
Completed IDs выводятся из mastery records, не дублируются вторым независимым key.
По одному best на редакцию оценки — не история всех попыток.
Это предложение schema в документе, не новый файл/миграция сейчас.

Выбор best: сначала mastery/gates, затем total в той же contentRevision/rubricVersion;
при равенстве сохранять прежнюю запись. Safety failure с высоким total не
вытесняет mastery. Новая редакция контента не делает старый best сопоставимым
молча; отмечать «пройдено по предыдущей версии», не удаляя прежнее достижение.
Retry никогда не вызывает удаление records. Сохранение serial read-modify-write
с обработкой false/exception, перечитыванием после ошибки и защитой double tap,
как принцип уже проверенного ProgressService, без изменения его ключа/логики.
SharedPreferences не обещает транзакции между ключами: envelope хранится одним
значением; история/resume/несколько писателей требуют отдельного решения позже.
Повреждённый/неизвестной версии practice payload показывает ошибку и не
перезаписывается пустым; старые завершённые уроки остаются доступными отдельно.

## 13. Предлагаемый пилот после утверждения

Минимум два обязательных кейса: dp01 (стартер) и dp13 (P0102).
Рекомендуемый третий — dp18 (SRS, только prepared messages): он проверяет,
что движок умеет засчитывать обоснованное ограничение вывода, а не всегда
требует найти физический компонент. Никакой SRS-measurement функциональности.

Этапы будущего разрешённого пилота, не начатые сейчас:
1. Согласовать этот контракт, safety, рубрику и два/три конкретных кейса.
2. Реализовать строгие pure Dart types/parser, конечные outcomes, attempt reducer,
   evidence rules и evaluator только в объёме пилота. Сначала unit tests.
3. Реализовать небольшой route controller, каталог/рабочий экран/журнал/вывод/
   оценку с real scroll widget tests. Хранение результатов — только если
   отдельно подтверждено, иначе пилот session-only с явно указанным ограничением.
4. Авторить два/три definitions после проверки физической согласованности,
   проверить альтернативные маршруты и невозможность зачёта угадывания.
5. Провести widget/integration и физический Android review, согласовать пользу
   и сложность. Остановиться для ревью, не добавлять остальные 15 кейсов автоматически.

MVP не включает visual wiring editor, свободное размещение любых щупов,
временной автомобильный solver, 3D, реальные DTC/scanner APIs или генератор кейсов.
Пилот успешен, если показывает различие догадки и доказанного вывода, сохраняет
весь draft при прокрутке и допускает несколько безопасных маршрутов.

## 14. Стратегия будущих unit/widget/integration тестов

Новые tests на R18.1 не создаются. Ниже требования к последующей реализации.

**Unit и data contract**:
- Строгий parsing всех sealed actions/results; ошибки типов, ссылок, units,
  неоднозначных/отсутствующих outcomes, запрещённого delivery; no fallback.
- Для каждой конечной допустимой комбинации — один детерминированный результат;
  неизвестные условия возвращают явный unavailable/blocked согласно definition.
- Табличная проверка dp01: 42 mA, 7.56+5.04=12.60 V, обратная полярность,
  иной возврат, I_motor=0 не закрывает proof исправности main cable.
- Табличная проверка dp13: divider 1.58416… V, open S=1.600/E=0,
  короткий путь не имитируется как open, unknown bias не становится 0.
- Immutable snapshot до/после смены профиля; старые records/оценка не меняются.
- Равнозначные proof sets и перестановки независимых действий дают те же E/I/D;
  недопустимое объединение timestamps/reference/нагрузок отвергается.
- Угадывание без проверок, ранняя замена, валидное недостаточно в confirmable,
  полный обоснованный referral dp18, safety gate, повторные записи без балльного фарма.
- Полнота матрицы альтернатив: в confirmable есть безопасный distinguishing set;
  в boundedDisposition сохраняются хотя бы две observationally equivalent причины.
- Retry/new attempt ID очищает session, не completed/best; evaluator не зависит
  от Flutter, wall clock, preferences или порядка JSON keys.

**Widget**:
- На 360 px выбрать первую проверку/точки/гипотезу/числовой draft, прокрутить
  к последним, выполнить там действие, вернуться; повторить три цикла и
  проверить сохранность **всех** selections и immutable evidence.
- Уничтожить/повторно создать видимые карточки, сменить вкладку, открыть/закрыть
  viewer, parent rebuild, resize/rotation, TextScaler 2.0 и клавиатура.
- Ровно одна итоговая отправка; до неё нет автоматического diagnosis reveal;
  после неё frozen controls, keyboard/focus protection, читаемый журнал.
- Missing rationale/evidence сообщает конкретный пробел; честное «недостаточно»
  доступно и не заблокировано только потому, что правильный компонент не выбран.
- Retry очищает всю попытку; save error сохраняет результат; pending write
  защищает от double submit/back/reset. Read error не превращается в пустой прогресс.
- Semantics labels, focus order, доступные/недоступные actions и причина запрета;
  нет overflow в light/dark, portrait/landscape, 360 px/увеличенном шрифте.

**Integration / устройство**:
- Home → Practice → каждый pilot → доказательный маршрут → submit → evaluation
  → explicit save (если persistence разрешён) → restart → сохранённый practice result;
  course completed IDs и 132-lesson denominator неизменны.
- Exit/reopen незавершённой session не восстанавливает ложный PASS; прерывание
  записи/ошибка storage не повреждает старый результат и не стирает курс.
- С отключённой сетью весь путь работает, нет permissions/запросов к адаптерам.
- Реальный Android: три цикла scroll, mixed actions, retry, TalkBack, large text,
  rotate/background, перезапуск. 919 прежних тестов — отдельный обязательный regression baseline.

7. Прежний курс, quiz HOTFIX, scoring и completed IDs без регрессии;

## 16. Риски, ограничения и STOP conditions

| Риск | Контроль / когда остановиться |
|---|---|
| Движок разрастается в solver машины | Только конечные profiles/points/outcomes; свободный circuit solver или произвольные scripts требуют отдельного проекта |
| Текст кейса раскрывает правильную деталь | Названия/симптомы без hidden fault; review альтернатив/очевидности, solution только после submit |
| Подготовленные данные физически противоречат друг другу | Проверка KCL/KVL/Ohm/units/окна и зависимостей; STOP до согласования корректной модели, не подгонка объяснения |
| Универсализация учебного MAF/ECU/BCM | Явные architecture/bias/profiles; неизвестный реальный интерфейс — insufficient, не догадка |
| Зачёт за угадывание или подбор всех кликов | Proof groups, связанные claims, safety gates, отсутствие повторного начисления |
| Навязана одна последовательность | Граф условий вместо сценарного списка «шаг 1…N»; alternative proof sets и permutation tests |
| Баллы стимулируют спешку/опасный короткий путь | Нет таймера/произвольных штрафов; 5% за обоснованность, safety/evidence не компенсируются |
| Потеря drafts как до quiz HOTFIX | Attempt/controller владеет всеми пользовательскими полями; scroll-disposal widget tests |
| Смешан старый прогресс и новый результат | Отдельный namespace/key и denominator; persistence только после отдельного разрешения |
| Неправомерная реальная процедура HV/SRS/ABS | STOP, заменить готовым read-only packet либо убрать action; не дописывать dangerous instructions |
