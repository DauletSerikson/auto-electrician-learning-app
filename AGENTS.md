Auto Electrician Learning App — инструкции для агента

Назначение проекта

Это портфолио-проект на Flutter для последовательного изучения
автомобильной электрики с начального уровня.

Приложение должно быть не электронной книгой, а интерактивной обучающей
средой. В проекте используются теория, иллюстрации, тесты, расчётные
задачи, интерактивные электрические цепи, виртуальный мультиметр,
упражнения по измерению падения напряжения и силы тока, диагностические
кейсы и отслеживание прогресса.

На текущем этапе приложение работает по принципу offline-first.

Не добавляй backend, авторизацию, облачные сервисы или функции
искусственного интеллекта без явного запроса владельца проекта.

Общая архитектура

Учебный контент отделён от пользовательского прогресса.

Учебные материалы: assets/course/

Текущие этапы: - stage_0 - stage_1 - stage_2

JSON-контент загружается через CourseService. Пользовательский прогресс
обслуживается через ProgressService.

Не смешивай учебный контент с пользовательским состоянием без
обоснованной архитектурной причины.

Архитектура LessonBlock

Блоки уроков используют типизированную sealed-иерархию.

Базовый тип: LessonBlock.

Конкретные типы включают: - TextLessonBlock - RememberLessonBlock -
WarningLessonBlock - ImageLessonBlock - QuestionLessonBlock -
CalculationLessonBlock - CircuitLessonBlock - MultimeterLessonBlock -
иерархию MeasurementLessonBlock - VoltageDropLessonBlock -
CurrentMeasurementLessonBlock - DiagnosticCaseLessonBlock -
DiagnosticChoiceLessonBlock

JSON должен преобразовываться в соответствующий конкретный subtype.

Не возвращай архитектуру к старой giant-модели LessonBlock с множеством
несвязанных nullable-полей.

Неизвестный тип блока и отсутствие обязательных данных должны приводить
к явной ошибке parsing/validation, а не к частично корректному объекту.

Сохраняй сильную статическую типизацию.

Рендеринг блоков

LessonScreen отвечает за состояние и завершение урока.

LessonBlockRenderer диспетчеризирует конкретные subtype LessonBlock в
соответствующие Flutter widgets.

Concrete widgets находятся в lib/widgets/lesson_blocks/.

Не возвращай диспетчеризацию обратно в LessonScreen.

При работе с LessonBlock предпочитай type-based pattern matching Dart
вместо строковых сравнений type, если нет конкретной причины поступить
иначе.

MeasurementLessonBlock

MeasurementLessonBlock — промежуточная абстракция для MeasurementBlock.

Она объединяет несколько измерительных упражнений: - напряжение
аккумулятора; - сопротивление провода; - прозвонку провода; - измерение
сопротивления.

Разные subtype имеют разные данные. Не делай все measurement-specific
свойства глобально обязательными только ради упрощения UI.

Симуляторы

Крупные simulator widgets сейчас могут одновременно содержать состояние,
расчётную/диагностическую логику, Flutter UI и обработку ввода.

В частности: - circuit_block.dart - measurement_block.dart -
current_measurement_block.dart - voltage_drop_block.dart -
diagnostic_case_block.dart - diagnostic_choice_block.dart -
multimeter_block.dart

Направление развития — постепенно отделять domain/simulation state и
расчётную логику от Flutter-представления.

Не переписывай все симуляторы одновременно. Сохраняй существующее
поведение, если задача явно не требует его изменения.

Известный технический долг

DiagnosticCaseBlock

Ранее выполненное измерение может отображаться с использованием текущего
состояния питания цепи. Из-за этого история измерений потенциально может
визуально измениться после переключения питания.

Будущее решение: сохранять неизменяемый snapshot/result измерения в
момент выполнения измерения.

Не исправляй это скрытно в несвязанном рефакторинге.

Проверка массы

Показание около 0 V относительно минусовой клеммы аккумулятора само по
себе не доказывает исправность массы под нагрузкой.

При развитии диагностики корректно различай потенциал, проверку под
нагрузкой, падение напряжения и высокое переходное сопротивление. Не
допускай технически неверного обучающего вывода.

Тестирование

Тесты — часть архитектуры проекта.

Существующие тесты охватывают, среди прочего: - JSON parsing
LessonBlock; - validation; - parsing уроков; - реальные course assets; -
согласованность модулей и уроков; - ID и порядок; - quiz metadata.

При изменении parsing/domain models обновляй или добавляй тесты.

При исправлении бага по возможности добавляй regression test.

Не удаляй тест только ради успешного test suite, если проверяемое
поведение намеренно не удалялось.

Учебный контент

Не переписывай учебные JSON-файлы без необходимости во время
архитектурного рефакторинга.

Изменение архитектуры и учебного содержания обычно выполняй отдельными
задачами.

Сохраняй совместимость с существующими course assets, если миграция
формата явно не входит в задачу.

Git workflow

Репозиторий: DauletSerikson/auto-electrician-learning-app

main считается стабильной веткой.

Перед существенными изменениями: 1. выполни git status; 2. изучи
актуальную реализацию; 3. найди callers/usages; 4. изучи связанные
тесты; 5. проверь текущий git diff.

Для существенных feature/refactor задач предпочитай отдельную ветку.

Без явного разрешения запрещено: - force push; - переписывать Git
history; - удалять ветки; - коммитить секреты; - push напрямую в main; -
создавать commit; - откатывать пользовательские изменения только потому,
что они мешают задаче.

Не создавай commit без явного запроса.

Перед предложением commit кратко опиши git diff, затронутые файлы и
результаты проверок.

Принципы разработки

Предпочитай: - небольшие контролируемые изменения; - сильную статическую
типизацию; - явные domain models; - читаемый Dart; - простые оправданные
абстракции; - тестируемую логику; - постепенный refactoring; -
минимальный необходимый scope.

Избегай: - speculative abstractions; - ненужных dependencies; - giant
rewrites; - premature backend architecture; - дублирования simulator
logic; - ослабления типов ради устранения analyzer errors; -
архитектурных паттернов ради самих паттернов.

Не добавляй Riverpod, Bloc, Provider, GetX или другой state-management
framework без доказанной необходимости и явного согласования.

Не внедряй сложную Clean Architecture только ради формального разделения
слоёв.

Безопасное изменение проекта

Перед редактированием: 1. изучи фактическую реализацию; 2. не полагайся
только на AGENTS.md; 3. изучи связанные модели; 4. найди usages/callers;
5. изучи тесты; 6. проверь незакоммиченные изменения.

После редактирования: 1. отформатируй затронутый код; 2. запусти
flutter analyze; 3. запусти flutter test; 4. изучи git diff; 5. проверь
соответствие scope поставленной задаче.

Не скрывай ошибки отключением lint, ослаблением типов, удалением
полезных тестов или необоснованным fallback.

Если требуется решение владельца, остановись и задай конкретный вопрос
вместо самостоятельного решения, существенно меняющего продукт или
архитектуру.

Работа с большими файлами

Не переписывай крупный simulator widget целиком без необходимости.

Перед рефакторингом: 1. определи ответственность существующего кода; 2.
найди состояние/расчёты для безопасного extraction; 3. сохрани внешнее
поведение; 4. выполняй изменение небольшими этапами; 5. проверяй проект
после каждого законченного этапа.

Предпочитай extraction/refactor вместо полного rewrite работающей
реализации.

Roadmap

R1 — Stabilization

Стабильный baseline, analyzer cleanup, parsing tests, проверки реальных
assets. Выполнен.

R2 — Typed Lesson Blocks

Typed sealed hierarchy, строгий JSON parsing, отказ от giant nullable
model, LessonBlockRenderer, typed widget inputs, удаление временного
compatibility layer.

Этап завершён только при чистом flutter analyze и успешном test suite.

R3 — Simulator/domain separation

Следующее крупное направление: постепенно отделить
физическую/диагностическую модель симуляторов от Flutter UI.

Сначала анализ существующих simulator widgets и безопасная
последовательность декомпозиции. Не начинай массовый rewrite.

R4 — Simulator architecture and correctness

Улучшение общей архитектуры, уменьшение дублирования, повышение
технической корректности диагностики, тестирование domain logic.

R5 — Progress/domain layer

План: completion, attempts, scores, unlocking, module progress и более
явная domain model прогресса. Не реализовывай заранее без отдельной
задачи.

R6 — Portfolio polish

README, screenshots, architecture diagram, дополнительные tests,
launcher icon, metadata, GitHub cleanup и release preparation.
